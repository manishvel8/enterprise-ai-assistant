🔭 What is Langfuse?

Open-source LLM observability platform. Like Sentry or Datadog — but built specifically for LLM applications.

Without Langfuse

  • Slow response? No idea which node caused it
  • Bad answer? Can't see what context was sent
  • High costs? Don't know which user/query is expensive
  • Agent looping? Can't see the sequence of tool calls
  • Quality degrading? No metric to track over time

With Langfuse

  • See exact latency per node (RAG: 350ms, LLM: 1.7s)
  • See exact prompt + context sent to LLM
  • Track cost per user/session/day
  • See full tool call sequence in trace tree
  • Filter traces by quality_score < 0.7
📐 Langfuse Hierarchy — Definitions
Trace Top-level container for ONE user request

Like a folder that holds everything that happened during one request. Attached to user_id, session_id.

Span A unit of work with duration

Any code block with a start + end time. Used for: LangGraph nodes, RAG retrieval, tool calls.

Generation An LLM API call

Special span that also tracks: model name, input tokens, output tokens, cost. Auto-cost for GPT models.

Event Point-in-time occurrence

No duration. Used for: human interruptions, decisions, errors, milestones.

Session Groups related traces

All traces from one browser tab / conversation window. session_id groups them for analysis.

User Groups all user activity

user_id on every trace groups all requests from one person. Enables per-user cost, latency, quality analysis.

Observation Generic term

Span, Generation, and Event all inherit from Observation in Langfuse's data model.

Score A numeric evaluation

Attached to a trace. Example: quality_score=0.92. Filter/sort traces by score in dashboard.

🔍 Debugging Scenarios

Scenario 1: Slow Response (4.8s instead of 1.8s)

In Langfuse: click the slow trace → expand spans

rag_retrieval: 3.1s  ← BIG RED FLAG (normal: 350ms)
  query_embedding: 48ms   ← OK
  vector_search: 3,050ms  ← QDRANT IS SLOW
response_generation: 1.7s ← normal

ROOT CAUSE: Qdrant query is slow because:
  → collection has 2M vectors but no index
  → Fix: Create ivfflat index on Qdrant collection
  → Or: Qdrant pod is under-resourced (CPU/RAM)

WHAT TO DO:
  curl http://localhost:6333/collections/chunks
  → check "vectors_count" and "indexed_vectors_count"
  → if indexed < total: collection not fully indexed

Scenario 2: Hallucinated Answer

In Langfuse: filter by quality_score < 0.5
→ Click offending trace
→ Expand "response_generation" span
→ Look at "evidence_chunks" = 0

ROOT CAUSE: RAG retrieved 0 chunks (empty_retrieval event present)
  The LLM had no context → made up an answer
  
TRACE SHOWS:
  EVENT: empty_retrieval (WARNING level)
    query: "What is Neha's salary at Google?"
    chunk_count: 0, threshold: 0.25
  SPAN: response_generation
    evidence_chunks: 0
    answer: "Neha earns $120K at Google" ← HALLUCINATION

FIX: Lower threshold / add more documents / add "I don't know" guardrail

Scenario 3: Cost Spike ($42/day instead of $18/day)

In Langfuse: Dashboard → Cost tab → sort by date
→ Yesterday: $42 (spike!)
→ Click → filter traces by that date

Pattern found: One user (user_id=user_999) made 500 requests
Each request has 12,000 input tokens (user is pasting huge documents into chat!)

FIX:
  1. Add rate limiting per user (10 requests/minute)
  2. Cap input token count in ChatRequest
  3. Add token-based context window management

Scenario 4: Agent Tool Loop

In Langfuse: filter traces with retry_count >= 3
→ Found 12 traces where quality_checker looped 3 times

Click one:
  response_generation (attempt 1): answer about RAG basics
  quality_check: REVISE — "Answer doesn't cite specific scores"
  response_generation (attempt 2): same answer
  quality_check: REVISE — same feedback
  response_generation (attempt 3): MAX RETRIES forced PASS

ROOT CAUSE: Quality checker feedback too vague (not actionable)
FIX: Make revision_feedback more specific in quality_checker system prompt

💡 How to Improve RAG Quality
RETRIEVAL PRECISION too low? (returning irrelevant chunks)
  → Increase score threshold (0.25 → 0.40)
  → Use hybrid search (vector + keyword BM25)
  → Better chunking strategy (smaller chunks, more overlap)

RETRIEVAL RECALL too low? (missing relevant chunks)
  → Lower score threshold (0.25 → 0.15)
  → Increase top_k (5 → 10)
  → Add query expansion / HyDE (Hypothetical Document Embeddings)

HALLUCINATION despite good retrieval?
  → Retrieved chunks too long → LLM ignores middle content
  → Fix: Re-rank chunks, keep only top 3, with higher quality
  → Fix: Add "only answer from context" to system prompt

EMPTY RETRIEVAL for known documents?
  → Check: is document actually in Qdrant collection?
  → Check: is query language same as document language?
  → Check: is embedding model same for storage and query?

🗓️ Session vs Conversation — Key Distinction

Conversation

The TOPIC. Created once. Can span many days and sessions.

conversation_id: conv_rag_001
title: "RAG Discussion"
created: Monday
messages: 24 (over 3 days)
status: active

Session

One VISIT. Created on each reconnect. Ends when user closes tab.

session_id: sess_9x4z     ← Monday 9am-10am
session_id: sess_7y2w     ← Tuesday 2pm-3pm
session_id: sess_3m8q     ← Wednesday 11am
→ All part of conv_rag_001
📊 Session Metrics
Analytics you can build from sessions table:
  
  Average session duration:
    SELECT AVG(EXTRACT(EPOCH FROM (ended_at - started_at))/60) FROM sessions
    Result: 23 minutes average
  
  Messages per session:
    SELECT AVG(message_count) FROM sessions
    Result: 8.2 messages/session
  
  Daily active sessions:
    SELECT DATE(started_at), COUNT(*) FROM sessions GROUP BY 1
  
  Drop-off sessions (started but no messages):
    SELECT COUNT(*) FROM sessions WHERE message_count = 0

🧠 Short-term vs Long-term Memory
Short-term Memory

What just happened in this session.

  • Recent 15-20 messages from this conversation
  • Current task/workflow state
  • LangGraph checkpoint (interrupt/resume)
Storage: PostgreSQL messages table + Redis (optional cache)
Lifespan: Session or conversation
Long-term Memory

What the app knows about the user across all conversations.

  • User preferences ("likes Python examples")
  • User facts ("senior backend engineer")
  • Instructions ("always use bullet points")
  • Past topics ("discussed RAG last week")
Storage: PostgreSQL memory table (with 1536-d vectors)
Lifespan: Permanent (or until user deletes)
🔍 Memory Retrieval Example
User says: "Give me the same style dashboard we discussed last week."

STEP 1: Embed the query
  embed("same style dashboard discussed last week")
  → vector [0.1, -0.3, 0.8, ...] (1536 floats)

STEP 2: Cosine search in memory table
  SELECT content, memory_type, similarity
  FROM memory
  WHERE user_id = 'user_demo_1'
  ORDER BY embedding <=> query_vector  ← pgvector operator
  LIMIT 5

STEP 3: Results (by similarity)
  similarity=0.91: "User prefers dark-themed grid layout dashboards"
  similarity=0.87: "User asked about dashboard design on 2026-09-14"
  similarity=0.74: "User uses Grafana and custom CSS for dashboards"

STEP 4: Inject into system prompt
  "Long-term memory about this user:
   - [Preference] User prefers dark-themed grid layout dashboards
   - [Episodic] User asked about dashboard design on 2026-09-14
   - [Fact] User uses Grafana and custom CSS for dashboards"

STEP 5: LLM now generates the right style without re-asking

🗄️ Schema Overview
  users (1 row per registered user)
    id (UUID PK) → external_id (from auth) → name → email → metadata → created_at
       ↓
  conversations (1 row per chat topic)
    id (UUID PK) → user_id (FK) → title → summary → message_count → total_tokens
       ↓
  sessions (1 row per browser visit)
    id (UUID PK) → conversation_id (FK) → user_id (FK) → thread_id → started_at → ended_at
       ↓
  messages (1 row per message)
    id (UUID PK) → conversation_id (FK) → session_id (FK) → role → content
    token_count → embedding VECTOR(1536) → model_used → langfuse_trace_id
       ↑
  memory (1 row per remembered fact)
    id (UUID PK) → user_id (FK) → memory_type → content → embedding VECTOR(1536)
    importance (0-1) → access_count → expires_at

🔍 Key Queries
-- All conversations for a user (latest first)
SELECT title, message_count, total_tokens, updated_at
FROM conversations
WHERE user_id = '00000000-0000-0000-0000-000000000001'
ORDER BY updated_at DESC;

-- Last 20 messages for context window
SELECT role, content, token_count, created_at
FROM messages
WHERE conversation_id = 'conv-uuid-here'
ORDER BY created_at DESC LIMIT 20;

-- Semantic search for relevant messages
SELECT role, content, 1 - (embedding <=> query_vec) AS similarity
FROM messages
WHERE conversation_id = 'conv-uuid'
ORDER BY embedding <=> query_vec
LIMIT 5;
🚀 Complete Production Request Flow

User sends: "Explain chunking again but relate it to my previous RAG question."
Click each step to see what happens internally.

1
Frontend → FastAPI POST /api/chat
Body: {query: "Explain chunking again...", user_id: "user_demo_1", conversation_id: "conv_rag_001"}
2
Auth & User Identification
get_or_create_user(external_id="user_demo_1") → {id: "uuid-001", name: "Manish"}
3
Conversation Lookup
get_conversation("conv_rag_001") → {title: "RAG Discussion", message_count: 8}
4
Load Recent History (sliding window)
get_recent_messages(conv_id, limit=50) → 8 messages
sliding_window(messages, max_tokens=20000) → last 8 fit (4,820 tokens)
5
Memory Retrieval (pgvector)
retrieve_relevant_memory(user_id, "chunking RAG question") → 3 memories:
• "User is building a RAG system" (similarity=0.89)
• "User prefers Python examples" (similarity=0.76)
6
Build Context Prompt
system = base_prompt + long_term_memory + conversation_summary
messages = [system] + recent_history + [current_query]
Token budget: sys=2K + mem=1K + msgs=5K + docs=40K + query=1K = 49K (< 128K)
7
Langfuse Trace Created
create_trace(request_id="req_a4b3c2d1", user_id="user_demo_1", session_id="sess_9x4z")
8
LangGraph: query_validator → router → rag_retriever
query_validator: is_valid=true (30ms)
router: heuristic → rag (mentions "RAG question", "previous") (22ms)
rag_retriever: "chunking RAG" → 5 chunks from docs (348ms)
9
LangGraph: response_generator → quality_checker
response_generator: GPT-4o generates answer with context + history (1842ms)
quality_checker: PASS (score=0.92) — answer is grounded and complete
10
Save Message + Flush Langfuse
save_message(role="assistant", content="...", token_count=380, latency_ms=2262)
finalize_trace(output=answer, success=True)
langfuse.flush() → sends all spans to http://localhost:3000
11
Return SSE Response to Client
Streaming response (node_update events) → final event with answer
Header: X-Conversation-ID: conv_rag_001 | X-Session-ID: sess_9x4z
