0. What must be running?

Short answer: Docker only for infra. LangGraph itself is a normal Python process. You do not need a new Docker stack only for LangGraph.

Required for LangGraph chat (read docs)

  • Docker: Qdrant (:6333) — vector search
  • Process: LangGraph app (:7860)
  • Config: OPENAI_API_KEY / gateway in langgraph-agent/.env

Optional: Tavily key for web-search path.

Required only when uploading a new PDF

  • Docker: Postgres, Redis, MinIO, Qdrant, Neo4j
  • Process: Backend API (:8000)
  • Process: Celery worker (PDF → chunks → embed)
  • Process: Angular UI (:4200) — upload screen

3. Hands-on: upload one document

Goal: put a PDF into MinIO + Postgres + Qdrant so LangGraph RAG can retrieve it.

UI Upload→ API :8000→ MinIO + Postgres→ Celery worker→ Parse → Chunk → Embed→ Qdrant chunks
1 Open Documents page
Browser → http://localhost:4200/documents
Where: Angular Documents page
2 Upload a PDF
Choose a resume/CV PDF (e.g. Resume_BhanuTeja_DS.pdf). Wait until status becomes complete and chunk count > 0.
Where: same Documents table — status column
3 If status stuck on processing
Celery worker must be running. In a terminal:
Terminal — Celery 
cd ~/Documents/Carrers/AI_Project/enterprise-ai-assistant/backend
source venv/bin/activate
celery -A app.workers.document_worker.celery_app worker \
  --loglevel=info --concurrency=2 --queues=document_processing
Where: worker terminal logs — Parsing → Chunking → Embedding → Stored
Important: LangGraph does not upload documents itself. It only reads the shared Qdrant collection chunks that the enterprise pipeline fills.
Technical: what happens on upload
  1. POST /api/documents/upload stores file in MinIO key documents/{doc_id}/original.pdf
  2. Inserts row in Postgres documents with status pending
  3. Enqueues Celery task on Redis queue document_processing
  4. Worker: PyMuPDF parse → clean → tiktoken chunk (800/100) → embed → Qdrant upsert
  5. Optional: Neo4j GraphRAG nodes (Document / Chunk / Person / Org)
  6. Status → complete, chunk_count updated

6. Technical: how one prompt is processed E2E

1 Validator→ 2 Router→ 3 RAG/ 3 Web/ 3 Human→ 6 Generator→ 7 Quality→ END

Example: “What are Bhanu Teja's skills and experience?”

StepNodeWhat happens (technical)Where you see it
0 UI → API POST /api/chat with query. FastAPI starts graph.astream(), returns SSE. DevTools Network EventStream; UI “Initialising…”
1 query_validator Structured LLM call → is_valid, sanitized_query. Gibberish/injection → END. Graph node green; Trace; State: validated_query
2 router Heuristics (resume/skills → rag) else LLM route: rag | web_search | needs_human. Route badge “📚 RAG”; State: route
3a rag_retriever Embed query (text-embedding-3-small) → Qdrant cosine search top_k=5, threshold 0.25 → chunks. Trace “Retrieved N chunks”; State: RAG Chunks
3b web_searcher (other path) Tavily search → titles/URLs/snippets. Web Searcher node; State: Web Results
3c human_gate (other path) interrupt() saves state; SSE interrupt; UI asks human; POST /api/chat/resume. Purple Human Gate panel
4 response_generator Builds numbered evidence from chunks → GPT-4o answer with [Source N] citations. State: Draft Answer
5 quality_checker LLM-as-judge: grounded + complete. PASS → END. REVISE → generator again (max 3). Quality bar %; Trace verdict; final chat bubble
6 SSE final API reads checkpointer snapshot → answer, sources, quality_score, full execution_trace. Center assistant message + source tags

Shared state (whiteboard every node writes to)

AgentState {
  original_query, validated_query, validation_result,
  route, route_reasoning,
  retrieved_documents[], web_results[],
  human_question, human_input,
  evidence, sources[], generated_response,
  quality_result, retry_count, max_retries,
  final_answer, is_complete,
  execution_trace[], errors[]
}
