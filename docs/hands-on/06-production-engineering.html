Why Two Backends? (FastAPI + LangGraph)

FastAPI backend (:8000)

  • Document upload → MinIO → Celery pipeline
  • Classic multi-agent RAG (chunk, embed, retrieve, answer, critic)
  • JWT login, documents API, health/metrics
  • Why: Fast, async Python API; great OpenAPI/Swagger; easy to protect with Depends()

LangGraph agent (:7860)

  • Stateful 7-node graph with branching (RAG / web / chat)
  • Human-in-the-loop via interrupt()
  • Durable checkpointer (Postgres) for multi-turn memory
  • Why: Graph = explicit control flow, retries, quality loop — hard to do cleanly in plain chains
Alternative to splitting: One monolith FastAPI app with LangGraph inside.
Why we split: Scale agents independently, isolate LLM latency from document API, clearer ownership for CI/deploy.
Request Flow — What Happens When You Ask a Question
1. UI — Angular sends query (optionally with JWT to FastAPI; LangGraph uses user_id/session)
2. Guardrails — length + injection regex run before any LLM call (cheap fail-fast)
3. query_validator — LLM confirms query is valid / sanitizes
4. router — chooses rag_retriever | web_searcher | general chat / human_gate
5. Retrieval — Qdrant (vectors) and/or Tavily (web) and/or Neo4j (relationships)
6. response_generator — GPT-4o builds answer from context
7. quality_checker — may reject and retry; then return + Langfuse trace

LangGraph 7-Node Graph — Why Each Node
NodeJobWhy not skip it?
query_validatorValidate / sanitize queryStops garbage + injection before spend tokens
routerPick RAG / web / chatWrong path = wrong answer or wasted retrieval
rag_retrieverQdrant searchGrounds answers in your documents
web_searcherTavily searchNeeded for fresh / external facts
human_gateHITL interruptCompliance / high-risk actions need a human
response_generatorWrite final answerCore LLM generation step
quality_checkerPass or retryReduces hallucinations / empty answers
Alternative graph designs: single “agent with tools” loop (ReAct) — simpler but harder to debug and enforce policy.
Why explicit nodes: each step is measurable in Langfuse, testable in pytest, and replaceable independently.
Checkpointer — MemorySaver vs PostgresSaver
MemorySaver (dev default)
• State in process RAM
• Pod restart = conversations gone
• Can’t safely run multiple replicas
• Fine for local learning
PostgresSaver (production)
• State in PostgreSQL
• Survives restarts
• Any replica can resume a thread
• Enables HPA scale-out
Enable: USE_POSTGRES_CHECKPOINTER=true
Alternatives: RedisSaver, SQLiteSaver, custom blob store.
Why Postgres here: we already run Postgres for conversations — one operational surface.

# Introduce a lint error
echo "import this_module_does_not_exist" >> app/main.py
